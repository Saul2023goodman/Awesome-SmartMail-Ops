# v1.41 上传后自动识别核验

## 为什么要前移“识别结果不对？”

来源分类发生在上传完成的一瞬间，用户此时还记得自己刚刚选了哪些文件、它们原本位于哪个目录、各自应该承担什么用途。若把纠错入口放到后续“待办”之后，用户必须先理解系统已经做错了什么，再逆向寻找来源设置，认知成本和误操作概率都会上升。

因此 v1.41 将来源分类核验视为**导入动作的收尾步骤**，不是异常诊断功能：

`选择文件 / 文件夹 → 自动读取与分类 → 立即核验分类 → 补充总名单 / 附件 → 处理邮件待办`

## UI 结构

### 1. 自动识别核验位于弹窗第一屏

上传完成弹窗不再先要求补总名单和附件，而是先回答“系统把我刚才的文件理解成什么”。顶部汇总邮件、名单、附件、未使用和待确认数量。

### 2. 保留原目录树

`webkitRelativePath / _nmdaPath` 直接生成树形结构。文件夹可折叠，文件行显示：

- 用途图标；
- 文件名；
- 用途文字；
- 判断状态与首要原因；
- 用途下拉框；
- 单文件“检查”。

颜色只作为辅助：邮件蓝、总名单紫、附件琥珀、未使用灰、建议检查橙；同时保留图标和文字，避免依赖色觉。

### 3. 单文件检查按需展开

过去“识别结果不对？”一次展示整批来源和字段映射，信息密度高且定位困难。现在只有点击某个文件时才展开检查器，并将集合列表限制到该文件相关的解析结果。若它被设为邮件，右侧才出现收件人、主题、正文等字段对应。

### 4. 0 封邮件也是正常可纠错状态

旧逻辑只有 `batch.tasks.length > 0` 才打开批次准备弹窗，导致“所有邮件都被误判为附件/未使用”时恰好失去最需要的纠错入口。v1.41 改为只要存在 dataset 就进入核验。

当当前为 0 封邮件时，总名单和附件补充卡暂时隐藏，避免用户在根因尚未修复前继续添加上下文；一旦将某来源改回邮件并生成任务，补充区自动出现。

### 5. 目录路径纠错必须真正生效

文件夹导入时 UI 使用 `folder/file.docx`，但解析集合的 source 可能只有 `file.docx`。旧版下拉纠错只传完整路径，存在找不到集合的风险。现在 `setSourcePurpose` 会同时尝试完整路径与 basename，保证目录树中的修改能落到实际集合。

## 交互原则

1. **错误在哪里发生，就在哪里修正。**
2. **先确认系统理解，再补充系统缺少的上下文。**
3. **批量视图用于扫一眼，单文件视图用于深查。**
4. **状态不能只靠颜色表达。**
5. **不确定来源默认不进入业务管线，但允许用户显式确认。**
6. **避免重复入口；高级字段映射属于当前文件检查的一部分，不再独立占据后续工作台。**
