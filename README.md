# NetEase Mail Draft Assistant v1.7.0

v1.7.0 重构联系人模块中的“邮箱读取”能力。核心变化不是扩大一个读取数量，而是把读取定义为 **Mailbox State Maintenance（邮箱状态维护）**。

## 读取的实质

读取不是联系人状态本身。系统现在明确拆成两层：

1. **邮箱证据层（可重建）**
   - 当前已发送文件夹中的邮件证据
   - 当前草稿箱中的邮件证据
   - 收件人、主题、时间、消息 ID
   - 当前发送计数、当前草稿计数、最近发送/草稿

2. **联系人决策层（人工/业务状态）**
   - 已回复
   - 待跟进
   - 暂停 / 不再联系
   - 自定义分类
   - 人工设置的互动阶段

完整重建只替换第一层，不覆盖第二层。

## 两种维护动作

### 快速刷新

内部读取最近 500 封已发送 + 最近 500 封草稿，增量合并新证据。适合日常工作。它不会清理本地旧快照，因此不会假装自己是“完整同步”。

### 完整重建

自动分页读取全部已发送与全部草稿。只有两个文件夹都被证明完整覆盖后，才会：

1. 在内存中建立全新邮箱快照；
2. 从快照重新计算发送次数、草稿次数、最近主题/时间等邮箱事实；
3. 保留人工联系人决策层；
4. 先成功写入 storage，再切换当前内存联系人库。

任何一个文件夹分页失败、停滞、达到安全上限或无法确认完整覆盖，本次完整重建直接失败，旧联系人库完全不修改。

## 安全语义

首次使用 v1.7 的“完整重建”会以当前邮箱为准纠正旧版累计出来的发送/草稿快照；不会把旧版 `sentCount` 自动当作不可撤销事实。自 v1.7 起，只有 Reader 实际观察到的发送才写入 `knownSentAt`。之后即使用户清理“已发送”文件夹，这条已确认观察过的发送事实仍可作为防重复联系的安全证据。

用户人工修改互动阶段时会标记 `stageSource = manual`；之后任何邮箱读取都不会覆盖这个阶段。

## Reader 架构

页面层只发送：

- `NMDA_READ_MAILBOX_STATE / quick`
- `NMDA_READ_MAILBOX_STATE / full`

后台 Reader 自己决定分页与读取策略，不再把“50 / 100 / 200 / 2000 / 全部”等技术范围暴露给用户。

完整读取保护上限提高到 100,000 封/文件夹、600 页；如果达到保护上限，结果会明确标记为 incomplete，绝不会用于 destructive rebuild。

## 联系人重建 API

`contacts.js` 新增：

- `cloneContacts()`
- `buildMailboxSnapshot()`
- `rebuildMailboxSnapshot()`
- `loadSyncMeta()`
- `saveSyncMeta()`

重建逻辑以快照替换邮箱事实，而不是在旧联系人对象上不断 `+1`。

## 回归重点

- 旧发送次数 99、邮箱真实只有 1 条 → 完整重建后当前计数为 1；
- 旧草稿数 5、草稿箱已没有 → 完整重建后为 0；
- 暂停 / 待跟进 / 自定义分类不丢失；
- 人工“已回复”不被邮箱重建覆盖；
- 新发现联系人可由完整快照建立；
- 人工阶段 override 在后续完整重建中继续保留。
