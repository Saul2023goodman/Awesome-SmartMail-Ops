# NetEase Mail Draft Assistant v1.6.0

v1.6.0 将数据摄取工作台从“识别结果 + 全字段映射 + 通用编辑表单”重构为 **Exception-driven Ingestion（异常驱动摄取）**。

核心原则：

> 机器负责完成确定的信息；人工只处理机器真正不知道的部分，并且人工判断必须能看到原始来源证据。

## 为什么要重构

v1.5.0 已经能够在极度混乱的 Word 中基于邮件原语识别 63 个邮件帧，其中 58 条核心信息完整，5 条真实缺少收件人邮箱。但旧工作台仍然把用户带回“编号 / 收件人 / 主题 / 正文 / 附件 / 定时 / 分类”的字段映射视图。

这会产生三个问题：

1. 机器已经正确识别的 58 条仍然占据主要 UI。
2. 真正需要处理的 5 条没有形成连续异常队列。
3. 人工校正脱离原始 Word 上下文，容易把邻近邮件的邮箱误填到当前邮件。

v1.6.0 因此把人工校正从“映射驱动”改成“异常驱动”。

## 新工作台主流程

```text
载入来源
   ↓
自动识别
   ↓
自动通过 ──────────────→ 保留
   ↓
待确认
   ↓
异常处理中心
   ↓
补齐 / 确认 / 明确排除
   ↓
附件匹配
   ↓
批次交接
   ↓
批量任务
```

主工作台不再要求普通用户理解 Sheet、表头、字段位置或 Word 结构。

结构诊断、内容集合、字段映射和识别模板被移动到折叠的“识别诊断与高级映射”区域，只在自动识别明显错误时使用。

## 自动识别结果

导入后首先显示批次健康状态：

- 识别邮件
- 自动通过
- 待人工确认
- 其他阻塞问题
- 已人工排除

困难案例预期为：

```text
识别邮件       63
自动通过       58
待人工确认      5
其他阻塞问题    0
```

不会再用“63 条任务 / 58 可用 / 5 error”这种工程状态要求用户自行理解。

## 异常处理中心

人工校正现在是三栏工作台：

### 1. 待确认队列

只列出需要人判断的邮件，例如：

- 缺少收件人
- 收件人邮箱格式无效
- 缺少主题
- 缺少正文
- 邮件边界证据不足

机器已经自动通过的邮件不会挤占这个队列。

### 2. 原文证据

每条 mail frame 在 Adapter 层保存自己的 `sourceContext`。因此即使多个 Word 合并成一个批次，每一封邮件仍然能够回到自己的原始文档上下文。

原文证据窗显示：

- 邮件前文
- 邮件识别范围
- 邮件后文
- Subject
- 称呼
- 落款
- 邮箱位置
- 身份标题 / heading 线索

邮件范围外的上下文降低视觉权重，避免误认为正文。

### 3. 最小校正

默认只突出真正存在问题的核心字段：

- 收件人
- 主题
- 正文

附件引用、定时和任务分类被放到“附加信息”折叠区，不再干扰核心邮件确认。

## 附近邮箱候选

对于缺收件人的邮件，系统会检查原文附近的邮箱，但这些值只作为人工候选，不自动写入。

候选评分综合：

- 与邮件边界的距离
- 是否带 `📧`
- 是否位于当前邮件范围内
- 邮箱 local-part 是否与 heading / 称呼中的姓名线索匹配
- 邮箱是否出现在邮件结束之后

出现在下一封邮件附近、且与当前姓名不匹配的邮箱会被强烈降权并从候选按钮中隐藏。

这专门防止困难 Word 中这种情况：

```text
Daniel Lock 邮件结束
契合点……
📧 m.chien@uq.edu.au
3. Monica Chien
Subject: ...
```

`m.chien@uq.edu.au` 会继续在原文证据窗中可见，但不会作为 Daniel Lock 的可靠一键候选。

## 人工确认状态

对于信息完整但证据置信度低的记录，用户不需要假装修改字段。

点击“保存 / 确认”即可写入当前批次的 `reviewConfirmed` 状态。之后软性边界警告不再重复进入人工队列，但收件人 / 主题 / 正文的硬缺失仍然不能被确认绕过。

## 明确排除

如果来源中某一段其实不是应该执行的邮件，或者可靠邮箱无法获得，可以点击：

`排除这封邮件`

它会从当前 MailTask 集合中移除，并计入“已人工排除”。

工作台提供“恢复已排除”，避免误操作不可逆。

## 批次交接闸门

“进入批量任务”不再只判断是否存在任务。

以下问题未解决时按钮会被禁用：

- 核心邮件信息仍待人工确认
- 无效收件人
- 无法解析的定时时间
- 缺失 / 歧义附件
- 其他非联系策略型预检错误

联系人“暂停 / 不再联系”仍按原有执行策略拦截，不被当作导入失败。

因此数据摄取工作台的输出现在真正满足：

> 交给执行层的 MailTask 应该已经完成信息理解和资源解析；执行层不再承担数据清洗职责。

## 来源证据模型

`mail-recognizer.js` 的 row metadata 现在保留：

- confidence
- evidence
- issues
- heading
- salutation
- closing
- sourceFile
- startBlock / endBlock
- recipientEvidence
- recipientCandidates

`import-adapters.js` 还为每封邮件保存紧凑的 `sourceContext` 窗口。

这使得人工校正不依赖当前格式：DOCX、TXT、HTML，以及未来 PDF/OCR Adapter 都可以使用同一套异常处理 UI。

## 困难案例回归

使用此前 80 页混乱 DOCX 对 v1.6 Mail Primitive pipeline 重新验证：

- ordered text blocks: 1192
- Subject anchors: 63
- salutations: 63
- closings: 63
- email occurrences: 58
- recognized mail frames: 63
- complete recipient + subject + body: 58
- real missing recipient records: 5
- average evidence confidence: 99%
- 每条 mail frame 均生成独立 sourceContext

核心识别数量与 v1.5 一致，v1.6 的变化集中在“如何让人真正有效地解决剩余不确定性”。

## 执行安全保持不变

- 只创建草稿，不自动发送。
- 每封填写完成必须主动点击网易“存草稿”。
- 普通草稿要求出现新的“成功保存到草稿箱”证据。
- 定时草稿要求出现“定时发信设置成功”证据。
- 当前封没有确认保存成功时立即停止批次，不进入下一封。
